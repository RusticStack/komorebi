# SMTP Send Boundary

Status: backend send boundary, live `lettre` SMTP transport, and pending Sent APPEND handoff implemented in Rust and exposed through the typed composer send command.
Last reviewed: 2026-05-23.

## Current Scope

The code source of truth is `src-tauri/src/smtp_send.rs`.

Komorebi sends outbound mail through a backend-only boundary that:

- Loads sender account metadata from SQLite by selected `account_id`.
- Resolves Gmail and Microsoft SMTP defaults when account rows do not override them.
- Requires generic IMAP/SMTP accounts to provide SMTP host, port, and security metadata.
- Resolves account-specific auth inside Rust.
- Loads stored non-secret OAuth client configuration before Gmail/Microsoft token refresh during composer sends.
- Composes MIME with `lettre`.
- Inserts the selected account's sanitized signature through the backend signature boundary.
- Streams attachment file bytes from app-generated storage paths in bounded chunks.
- Records local sent state only after the SMTP transport returns an accepted response.
- Converts a supplied active draft id to sent state only after confirmed SMTP acceptance.
- Updates local-only recent-recipient autocomplete rows after confirmed composer sends.
- Stores the exact RFC822 payload for provider policies that need a later IMAP Sent-folder APPEND.

The module remains the SMTP source of truth. The frontend does not call it directly; `src-tauri/src/composer.rs` exposes `send_composer_email` as the reviewed Tauri command wrapper. That wrapper validates the active draft request, staged attachment ownership, and sanitized body payloads before resolving credentials or calling SMTP.
The wrapper also deduplicates To/CC/BCC recipients before send and best-effort updates `recent_recipients` after SMTP acceptance.

## Account And Transport Resolution

`SqliteSmtpAccountStore` reads only non-secret account metadata from `accounts`:

- `provider_kind`
- `display_email`
- `display_name`
- `username`
- `auth_kind`
- `smtp_host`
- `smtp_port`
- `smtp_security`
- `signature_html`

Provider defaults:

- Gmail: `smtp.gmail.com`, port `587`, STARTTLS.
- Microsoft: `smtp.office365.com`, port `587`, STARTTLS.
- Generic IMAP/SMTP: SMTP host, port, and security are required in the account row.

SMTP hosts must be host names, not URLs, paths, or credential-bearing strings. Authenticated SMTP over `smtp_security = none` is denied before a network connection is attempted. `tls` and `starttls` are the accepted authenticated transport modes.

`LettreSmtpSender` is the production live SMTP adapter. It uses TLS wrapper mode for `tls`, required STARTTLS for `starttls`, provider-specific AUTH mechanisms (`PLAIN` for compatible generic providers and `XOAUTH2` for Gmail/Microsoft), a bounded timeout, and redacted transport errors. Plaintext SMTP is available only to unit tests through an internal loopback-only constructor so the live adapter can be verified against a local protocol fixture without weakening production transport policy.

## Authentication

`BackendSmtpAuthResolver` enforces the provider/auth matrix from `src-tauri/src/auth.rs`:

- Gmail and Microsoft use OAuth2/XOAUTH2 only.
- Generic compatible providers may use app-password/manual-password auth through the `generic-password` credential slot.
- Generic provider OAuth2 remains unsupported until provider-specific issuers, scopes, and token behavior are defined.

OAuth send paths call `TokenLifecycle::ensure_access_token` inside Rust. Access tokens, refresh tokens, and passwords are never returned to React or persisted in SQLite. Refresh failure becomes a reconnect-needed backend state instead of exposing a secret.

## MIME Composition

Outbound messages are composed with `lettre::Message`:

- From comes from the selected account display email/name.
- To, CC, BCC, and Reply-To are typed address records and validated before auth resolution.
- BCC participates in the SMTP envelope but is not preserved in formatted message headers.
- Plain text, sanitized HTML, and plain+HTML multipart alternatives are supported.
- Sanitized rich composer HTML preserves the reviewed subset for strikethrough, tables, inline code, code blocks, alignment, font family, font size, text color, and highlights.
- Account signatures are sanitized and inserted with the deterministic managed signature block from `docs/architecture/account-signatures.md`.
- Attachments are wrapped in multipart/mixed when present.
- Inline attachments use CID metadata when available.
- RFC `Message-ID` is generated by Rust unless a valid caller-supplied Message-ID is provided.

HTML input is accepted only through `SanitizedHtml`. Raw script tags, JavaScript URLs, and inline event-handler patterns are rejected by the outbound boundary. The TipTap composer sanitizes generated HTML before IPC, limits rich formatting styles to the reviewed whitelist in `src/mail/composer/composerRichText.ts`, rewrites inline uploaded images to staged attachment CIDs, and the command wrapper constructs `SanitizedHtml` before send.

Stored `accounts.signature_html` values are sanitized again before insertion so legacy or fixture rows cannot bypass the outbound boundary. HTML signatures replace an existing managed signature block instead of duplicating it. Text-only sends receive a derived plain-text signature with the standard `-- ` delimiter.

## Attachment Streaming

Outbound attachment requests carry backend attachment IDs only. They do not carry paths.

For composer-originated files, `stage_composer_attachment` writes selected bytes to backend-generated app-data paths and stores metadata in `composer_attachments`. `send_composer_email` streams those staged files through `ComposerAttachmentStore`. The WebView never receives or sends local filesystem paths.

`FilesystemAttachmentStore`:

- Looks up attachment metadata by `(account_id, attachment_id)`.
- Requires a non-null `storage_relative_path`.
- Rejects absolute paths, `..`, root/prefix components, and paths that canonicalize outside the configured app storage root.
- Reads files in chunks no larger than `ATTACHMENT_STREAM_CHUNK_BYTES` (`64 KiB`).
- Enforces `MAX_OUTBOUND_ATTACHMENT_BYTES` (`25 MiB`) per attachment.
- Enforces a bounded aggregate outbound message size before accumulating attachment bytes for `lettre`.
- Verifies the actual file byte count matches the stored attachment metadata.

`lettre` owns MIME parts as in-memory values before transport send. The boundary keeps memory bounded by rejecting oversized attachments/messages and streaming source files in chunks before handing validated parts to `lettre`; it is not a zero-copy transport.

## Confirmed Send State

Migration `004_smtp_send_receipts.sql` adds `smtp_send_receipts`.

The receipt records:

- Account id.
- RFC Message-ID.
- Subject and sender address.
- To/CC/BCC JSON address snapshots.
- Attachment IDs.
- SMTP host, port, security, and auth mechanism.
- Composed message size.
- Provider response summary.
- `sent_at`/`created_at` timestamps.

`send_email` inserts a receipt only after `SmtpSender::send` succeeds. Transport failure returns an error and leaves `smtp_send_receipts` unchanged.

When a source draft id is supplied, `send_email` validates that the draft is active before auth/network work. After SMTP acceptance, it inserts the receipt, marks the draft sent, clears private draft content, and writes the provider-aware `sent_mail_copies` record in one transaction. When that record is `imap_append/pending_upload`, the same transaction stores the formatted RFC822 payload and SHA-256 for retry by the sync scheduler.

Provider-aware Sent-copy planning and pending IMAP APPEND upload are implemented in `docs/architecture/draft-and-sent-persistence.md`. Gmail rows remain `provider_auto_copies/not_required` and do not retain or upload APPEND payloads.

## Tests

`src-tauri/src/smtp_send.rs` tests cover:

- Generic account send with account-specific SMTP metadata.
- Gmail default SMTP metadata with XOAUTH2.
- Password and OAuth auth resolution without exposing secrets through debug output.
- Failed SMTP delivery leaving no sent receipt.
- Failed SMTP delivery leaving the source draft active.
- Confirmed SMTP delivery converting the source draft to sent state.
- Confirmed SMTP delivery retaining a temporary RFC822 APPEND payload for Microsoft/generic rows that require Sent upload.
- Sanitized account signature insertion during MIME composition.
- Rich composer HTML serialization for strikethrough, tables, code blocks, font controls, colors, highlights, and alignment.
- BCC header removal from formatted MIME.
- Attachment chunk streaming through a fake attachment store.
- Attachment storage path traversal denial under a temp root.
- Unsafe HTML, invalid recipient, missing body, missing recipient, invalid attachment ID, URL-like SMTP host, and plaintext authenticated SMTP denial paths.
- `LettreSmtpSender` delivery against a local loopback SMTP fixture for PLAIN and XOAUTH2 without exposing secrets in message DATA, plus redacted auth-failure mapping.

`src-tauri/src/schema.rs` tests cover migration from schema version 3 to version 4, valid receipt insertion, and later draft/composer attachment migrations.

`src-tauri/src/composer.rs` tests cover the frontend-callable send wrapper with fake SMTP/auth and staged attachments.
They also cover duplicate recipient normalization, stored Gmail/Microsoft OAuth client config loading for composer sends, and local recent-recipient persistence after confirmed fake SMTP send.

`src-tauri/tests/protocol_fixtures.rs` tests cover a socket-level SMTP fixture:

- EHLO capability advertisement.
- AUTH success and AUTH failure denial.
- MAIL FROM, RCPT TO, DATA, and QUIT command flow.
- Captured message DATA payloads for assertions without a live SMTP server.

`src-tauri/tests/live_smtp_smoke.rs` is ignored by default and runs only when the user explicitly opts in with `KOMOREBI_LIVE_SMTP_SMOKE=1` and supplies test-account environment variables. It creates a disposable SQLite cache, writes the test secret to Windows Credential Manager under a generated account id, sends through `send_composer_email_from_path`, verifies `SmtpAccepted`/`SentStateRecorded`, and deletes the temporary credential/app-data directory afterward.

Normal checks do not use a live mailbox, live SMTP server, real account, or real credential.
