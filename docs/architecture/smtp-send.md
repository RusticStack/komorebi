# SMTP Send Boundary

Status: backend send boundary implemented in Rust; no frontend-callable command is registered.
Last reviewed: 2026-05-22.

## Current Scope

The code source of truth is `src-tauri/src/smtp_send.rs`.

Komorebi sends outbound mail through a backend-only boundary that:

- Loads sender account metadata from SQLite by selected `account_id`.
- Resolves Gmail and Microsoft SMTP defaults when account rows do not override them.
- Requires generic IMAP/SMTP accounts to provide SMTP host, port, and security metadata.
- Resolves account-specific auth inside Rust.
- Composes MIME with `lettre`.
- Streams attachment file bytes from app-generated storage paths in bounded chunks.
- Records local sent state only after the SMTP transport returns an accepted response.

The current module is not wired to `invoke_handler` and does not grant frontend command permissions. That keeps the existing zero-permission Tauri capability posture intact until account setup, composer UI, draft state, command ACL, and command-specific UI validation exist.

## Account And Transport Resolution

`SqliteSmtpAccountStore` reads only non-secret account metadata from `accounts`:

- `provider_kind`
- `display_email`
- `display_name`
- `username`
- `auth_kind`
- `smtp_host`
- `smtp_port`
- `smtp_security`

Provider defaults:

- Gmail: `smtp.gmail.com`, port `587`, STARTTLS.
- Microsoft: `smtp.office365.com`, port `587`, STARTTLS.
- Generic IMAP/SMTP: SMTP host, port, and security are required in the account row.

SMTP hosts must be host names, not URLs, paths, or credential-bearing strings. Authenticated SMTP over `smtp_security = none` is denied before a network connection is attempted. `tls` and `starttls` are the accepted authenticated transport modes.

## Authentication

`BackendSmtpAuthResolver` enforces the provider/auth matrix from `src-tauri/src/auth.rs`:

- Gmail and Microsoft use OAuth2/XOAUTH2 only.
- Generic compatible providers may use app-password/manual-password auth through the `generic-password` credential slot.
- Generic provider OAuth2 remains unsupported until provider-specific issuers, scopes, and token behavior are defined.

OAuth send paths call `TokenLifecycle::ensure_access_token` inside Rust. Access tokens, refresh tokens, and passwords are never returned to React or persisted in SQLite. Refresh failure becomes a reconnect-needed backend state instead of exposing a secret.

## MIME Composition

Outbound messages are composed with `lettre::Message`:

- From comes from the selected account display email/name.
- To, CC, BCC, and Reply-To are typed address records and validated before auth resolution.
- BCC participates in the SMTP envelope but is not preserved in formatted message headers.
- Plain text, sanitized HTML, and plain+HTML multipart alternatives are supported.
- Attachments are wrapped in multipart/mixed when present.
- Inline attachments use CID metadata when available.
- RFC `Message-ID` is generated by Rust unless a valid caller-supplied Message-ID is provided.

HTML input is accepted only through `SanitizedHtml`. Raw script tags, JavaScript URLs, and inline event-handler patterns are rejected by the outbound boundary. The composer still needs a frontend sanitizer/editor integration before the send path can be exposed to users.

## Attachment Streaming

Outbound attachment requests carry backend attachment IDs only. They do not carry paths.

`FilesystemAttachmentStore`:

- Looks up attachment metadata by `(account_id, attachment_id)`.
- Requires a non-null `storage_relative_path`.
- Rejects absolute paths, `..`, root/prefix components, and paths that canonicalize outside the configured app storage root.
- Reads files in chunks no larger than `ATTACHMENT_STREAM_CHUNK_BYTES` (`64 KiB`).
- Enforces `MAX_OUTBOUND_ATTACHMENT_BYTES` (`25 MiB`) per attachment.
- Enforces a bounded aggregate outbound message size before accumulating attachment bytes for `lettre`.
- Verifies the actual file byte count matches the stored attachment metadata.

`lettre` owns MIME parts as in-memory values before transport send. The boundary keeps memory bounded by rejecting oversized attachments/messages and streaming source files in chunks before handing validated parts to `lettre`; it is not a zero-copy transport.

## Confirmed Send State

Migration `004_smtp_send_receipts.sql` adds `smtp_send_receipts`.

The receipt records:

- Account id.
- RFC Message-ID.
- Subject and sender address.
- To/CC/BCC JSON address snapshots.
- Attachment IDs.
- SMTP host, port, security, and auth mechanism.
- Composed message size.
- Provider response summary.
- `sent_at`/`created_at` timestamps.

`send_email` inserts a receipt only after `SmtpSender::send` succeeds. Transport failure returns an error and leaves `smtp_send_receipts` unchanged.

This is not full Sent-folder synchronization. Uploading/synchronizing the sent copy to a provider Sent folder remains a separate draft/Sent semantics task.

## Tests

`src-tauri/src/smtp_send.rs` tests cover:

- Generic account send with account-specific SMTP metadata.
- Gmail default SMTP metadata with XOAUTH2.
- Password and OAuth auth resolution without exposing secrets through debug output.
- Failed SMTP delivery leaving no sent receipt.
- BCC header removal from formatted MIME.
- Attachment chunk streaming through a fake attachment store.
- Attachment storage path traversal denial under a temp root.
- Unsafe HTML, invalid recipient, missing body, missing recipient, invalid attachment ID, URL-like SMTP host, and plaintext authenticated SMTP denial paths.

`src-tauri/src/schema.rs` tests cover migration from schema version 3 to version 4 and valid receipt insertion.

No test uses a live mailbox, live SMTP server, real account, or real credential.

## Not Implemented

- Frontend composer wiring.
- Tauri `send_email` IPC registration and capability grant.
- Draft autosave/discard/restore semantics.
- Sent folder upload or provider-specific append behavior.
- SMTP protocol-level fake server.
- Live account setup and live SMTP integration tests.
